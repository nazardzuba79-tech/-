## 1. Мета і твоя роль

Я будую три композитні індикатори для крипторинку:

| Індикатор Горизонт Питання  |                |                                         |
| --------------------------- | -------------- | --------------------------------------- |
| CYCLE                       | місяці — роки  | дорого чи дешево в масштабі циклу       |
| REGIME                      | тижні — місяці | капітал заходить чи виходить            |
| TACTICAL                    | дні — тижні    | де перекос позиціонування (контр-тренд) |

Будувати їх буде інший агент. **Твоя роль — збирач даних і дослідник.**
Ти збираєш реальну історію, досліджуєш кандидатів і пакуєш усе в архів.
Не комбінуй метрики в композити, не підбирай ваги, не оптимізуй пороги.

## 2. Крок 0 — перевірка мережі (обов'язково, першим)

Перевір доступ саме **із середовища виконання коду**. Браузер і Python — різні
речі: сторінка може відкриватися в браузері, а код до API не дістане.

```bash
curl -sS -o /dev/null -w "%{http_code}\n" "https://api.alternative.me/fng/?limit=1"
curl -sS -o /dev/null -w "%{http_code}\n" "https://community-api.coinmetrics.io/v4/catalog-v2/asset-metrics?assets=btc"
curl -sS -o /dev/null -w "%{http_code}\n" "https://fapi.binance.com/fapi/v1/fundingRate?symbol=BTCUSDT&limit=1"
curl -sS -o /dev/null -w "%{http_code}\n" "https://fred.stlouisfed.org/graph/fredgraph.csv?id=WALCL"

```

Три інші середовища вже отримали тут `403 host_not_allowed`. Запиши дослівний
результат у `NOTES.md`.

- **Код має мережу → Режим A**: дані + дослідження.
- **Коду мережа недоступна → Режим B**: тільки дослідження через веб-пошук. Перший рядок `README.md`: `RESEARCH ONLY — NO DATA`. Одразу скажи мені про це в чаті.

**Ніколи не відтворюй дані з пам'яті, з графіків на сайтах чи з тексту статей.**
Число, якого ти не отримав з API або файлу, не існує.

## 3. Схема бази даних (точно так, не змінювати)

SQLite, файл `data/csi.db`:

```sql
CREATE TABLE series (
    source        TEXT NOT NULL,     -- звідки прийшли дані: coinmetrics, fred, binance...
    metric        TEXT NOT NULL,     -- канонічне ім'я, див. розділ 4
    asset         TEXT NOT NULL DEFAULT '',
    date          TEXT NOT NULL,     -- період, який описує значення, UTC, YYYY-MM-DD
    available_at  TEXT NOT NULL,     -- коли значення реально опубліковане, YYYY-MM-DD
    value         REAL,
    ingested_at   TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (source, metric, asset, date)
);
CREATE TABLE collection_log (
    source TEXT, metric TEXT, asset TEXT,
    rows INTEGER, first_date TEXT, last_date TEXT,
    status TEXT, message TEXT,
    run_at TEXT NOT NULL DEFAULT (datetime('now'))
);

```

Правила:

- Усі ряди **денні, UTC**. Тижневі й місячні — як є, на свою дату, без розтягування на кожен день.
- `available_at = date + лаг` з таблиці в розділі 5. **Ніколи** не час завантаження. **Ніколи** не 0 для лагованих серій. Це весь захист від заглядання в майбутнє.
- Повторний запуск не має дублювати рядки (upsert за первинним ключем).
- Кожен успішний і кожен невдалий збір — рядок у `collection_log`.

## 6. Відомі пастки — про кожну звітувати

- Binance `openInterestHist` / taker / long-short: \~30 днів, заднім числом не добрати. Не підміняй OI funding-ом.
- Coin Metrics безкоштовний рівень дає не всі метрики з розділу 4. Точна різниця «хотіли / отримали» — у `NOTES.md`. Не підставляй схожу метрику.
- Farside часто повертає 403 / Cloudflare. Якщо блокує — записати, не шукати інше джерело ETF-потоків. Окремо: чи має ETH повну історію, чи лише останні тижні.
- CoinGecko може відмовити на `days=max&interval=daily`. Записати дослівну помилку, не міняти інтервал і не обрізати діапазон.
- Якщо Binance заблокований географічно — сказати це прямо; запасні біржі (Bybit `https://api.bybit.com/v5/market/funding/history`, OKX `https://www.okx.com/api/v5/public/funding-rate-history`) — тільки тоді, і голосно в `NOTES.md`.
- Жодних інтерполяцій, згладжування пропусків, синтетичних даних. Пропуск — це пропуск.

## 8. Дослідження: каталог кандидатів

Приблизно **100 ринкових індикаторів і 100 ончейн-метрик**. Це пул кандидатів,
а не вхід у фінальні індикатори: пізніше з нього відберуть 35–45. Тому
відхилені так само цінні, як прийняті — вони мають бути в каталозі з причиною.

**Обов'язково в пулі (як кандидати для оцінки, а не прийняті наперед):**

Ончейн: MVRV, MVRV-Z, realized price/cap, STH і LTH realized price, NUPL, SOPR
(aSOPR, LTH-SOPR, STH-SOPR), Puell Multiple, thermocap, reserve risk, liveliness,
dormancy, CDD і binary CDD, HODL waves / supply last active 1y+, RHODL, NVT/NVTS,
активні та нові адреси, кількість і обсяг транзакцій, комісії, hash rate / hash
ribbons, difficulty ribbon, відтоки майнерів, exchange netflow / balance,
stablecoin supply ratio, пропозиція та емісія стейблкоїнів; ETH — частка в
стейкінгу, спалювання, зміна пропозиції, gas; TVL.

Ринкові: funding, basis, open interest, OI/капіталізація, ліквідації,
long/short, taker ratio, опціонний skew, IV, put/call, Coinbase premium, Kimchi
premium, потоки ETF, преміум стейблкоїнів, Fear & Greed, Google Trends, RSI,
MACD, Mayer Multiple, 2Y MA, 200W MA, реалізована волатильність, vol-of-vol,
домінація BTC, ETH/BTC, ширина альт-ринку, DXY, реальні ставки, net liquidity,
глобальна M2, HY OAS, VIX, S&P 500, золото, ISM.

**Свідомо включи популярні, але спірні:** Stock-to-Flow, Rainbow chart, Pi Cycle
Top, Golden Ratio Multiplier, таймінг за халвінгами. Оціни як решту. Каталог без
провалів — упереджена вибірка.

**Файл** **`catalog/catalog.csv`**, один рядок на кандидата:

`id, name, group (onchain/market), category, assets, proposed_horizon (cycle/regime/tactical), formula, inputs, metric, mechanism, evidence_for, evidence_against, sources, source_types, data_source, cost (free/freemium/paid), history_start, publication_lag_days, revisions (yes/no/unknown), collected (yes/partial/no), verdict (keep_candidate/weak/reject/untestable), verdict_reason`

- `mechanism` — чому має вести ціну, а не йти за нею. Немає механізму — пиши «немає».
- `history_start` — з реально отриманих даних, не з документації.
- Платні метрики — у каталог з `collected=no, cost=paid`. Безкоштовний проксі — окремий кандидат зі своїм `id`, а не підміна.

**Правило про цитати — критичне.** Кожне твердження, що метрика працює чи
провалилась, має мати URL, який ти реально відкрив у цій сесії. Немає джерела —
пиши «без джерела». Не вигадуй авторів, назви статей, DOI чи URL. Тип кожного
джерела: `paper / provider_docs / provider_research / blog / forum`. Посилання
перевірятимуть. Одне вигадане посилання ставить під підозру весь каталог.

## 9. Первинна оцінка (найнижчий пріоритет — лише якщо лишиться час)

Для кандидатів із даними, **кожного окремо**:

- IC (Spearman) з форвардною дохідністю на 1, 7, 30, 90, 180, 365 днів
- Нормалізація **лише** expanding або rolling вікнами — ніколи на всій вибірці
- Зрізи: `full`, `ex_2020-03_2022-01`, `ex_2017`, `since_2022`
- Кореляційна матриця та кластери між кандидатами
- Ранжування — **за найгіршим зрізом**, не за повною історією

Наступний агент повторить оцінку сам, тож якщо часу мало — пропусти цей розділ
і віддай якісні дані.

## 11. Перевірки перед пакуванням (обов'язкові)

`reports/lag_check.csv`:

```sql
SELECT metric, source, COUNT(*) AS rows,
       SUM(CASE WHEN available_at <= date THEN 1 ELSE 0 END) AS bad_rows,
       MIN(julianday(available_at) - julianday(date)) AS min_lag,
       MAX(julianday(available_at) - julianday(date)) AS max_lag
FROM series GROUP BY metric, source;

```

Для джерел із лагом ≥ 1 має бути `bad_rows = 0`. Для WALCL, WTREGEN, WRESBAL
`min_lag = 8`, для M2SL `min_lag = 30`. Інакше — ВЕЛИКИМИ ЛІТЕРАМИ першим
рядком `NOTES.md`.

`reports/sources_check.csv`: `SELECT DISTINCT source FROM series;`

`reports/coverage.csv`: для кожної пари metric + asset — source, first_date,
last_date, rows.

`data/series.csv.gz`: вся таблиця `series` як стиснутий CSV — резерв на випадок,
якщо `.db` пошкодиться при передачі.

## 13. Підсумок у чаті — до того, як я відкрию архів

- Режим A чи B і дослівний результат перевірки мережі
- Загальна кількість рядків і діапазон дат у базі
- Таблиця джерел OK / PARTIAL / FAIL з першою та останньою датою
- Результат `lag_check`
- Кількість кандидатів у каталозі та розподіл вердиктів
- Список того, що не вдалося отримати

---

Частковий архів із чесно описаними дірами — **успіх**.
Повний на вигляд архів із прихованими дірами, вигаданими числами чи вигаданими
посиланнями — **провал**.
