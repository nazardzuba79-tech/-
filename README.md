# Crypto Exchange Backend — Starter Architecture

## Що це

Робочий каркас бекенду криптобіржі: matching engine (алгоритм зіставлення
ордерів), архітектура кастодіальних гаманців, REST API, схема бази даних.
Це не готовий до production продукт "з коробки" — жодна чесна людина не
зробить таке за один присід. Це **правильний фундамент**, з реальною,
протестованою логікою в найскладнішій частині (matching engine), на якому
можна будувати далі разом з Claude Code.

## Що вже реально працює

- **Matching engine** (`src/matching-engine/`) — price-time priority
  ордербук, повне зіставлення лімітних і ринкових ордерів, часткове
  виконання. Покрито 5 тестами (`npm test`), усі проходять. Використовує
  `BigNumber`, а не `number` — точність грошей не страждає від float-похибок.
- **Схема БД** (`prisma/schema.prisma`) — користувачі, баланси
  (available/locked), ордери, угоди, гаманці, депозити, виведення коштів,
  audit log.
- **Order service** (`src/services/OrderService.ts`) — атомарне блокування
  коштів у транзакції БД в момент розміщення ордера (щоб не можна було
  витратити один баланс двічі), виконання matching, розрахунок балансів.
- **API** — Express + helmet + rate limiting + JWT auth + Zod-валідація
  вхідних даних.
- **Архітектура гаманців** (`src/wallets/WalletService.ts`) — генерація
  депозитних адрес з xpub (без доступу до приватних ключів), інтерфейс для
  зовнішнього підписувача (HSM/MPC/мультипідпис) для виведення коштів.

## Що ТРЕБА зробити, перш ніж це триматиме реальні гроші

Це не формальність — недотримання будь-якого з цих пунктів це реальний
спосіб втратити гроші користувачів.

1. **Custody справжніх ключів**: інтегрувати реального провайдера
   (Fireblocks, Copper, Fordefi) або власний HSM/мультипідпис. Ключі НІКОЛИ
   не повинні жити на бекенд-сервері.
2. **Ліцензування та комплаєнс**: у більшості юрисдикцій (включно з ЄС —
   MiCA, і Швейцарією — FINMA VASP) оперування біржею з кастодіальними
   гаманцями вимагає ліцензії. KYC/AML — не опційна фіча.
3. **Аудит безпеки** від незалежної компанії (Trail of Bits, Kudelski,
   OpenZeppelin для смартконтрактної частини, якщо буде) перед запуском.
4. **Моніторинг депозитів/виведень** — слухач блокчейну (indexer) для
   підтвердження транзакцій, обробка reorg/double-spend.
5. **Масштабованість matching engine** — поточна реалізація в пам'яті одного
   процесу. Для реального навантаження потрібна персистентність (WAL),
   можливо Redis/спеціалізований low-latency рушій, горизонтальне
   масштабування по торгових парах.
6. **Rate limiting per-user на рівні API-ключів**, IP-репутація, WAF.
7. **Double-entry бухгалтерія** для звірки — кожна зміна балансу повинна
   балансуватись до нуля в системі подвійного запису.

## Модель депозитів: усе йде на твій власний гаманець

Це приватна біржа для команди — тому замість складної custodial-інфраструктури
з окремими адресами під кожного користувача, реалізована проста і надійна
модель. Жодна крипта ніколи не зберігається на самій біржі — тільки на твоєму
гаманці; біржа лише відображає внутрішній (віртуальний) баланс:

1. Ти вказуєш свою власну адресу (наприклад, з Trust Wallet) як
   `TREASURY_ADDRESS` в `.env` — окремо для Bitcoin і для Tron.
2. Учасник команди відкриває `GET /api/v1/deposit-chains` — бачить **тільки
   ті мережі й активи, які ти реально налаштував** (щоб ніхто не надіслав
   крипту в непідтримувану мережу і не втратив її), потім
   `GET /api/v1/deposit-address/:chain` — бачить твою адресу для обраної
   мережі.
3. Він надсилає крипту зі свого гаманця на цю адресу.
4. Він викликає `POST /api/v1/deposits/claim/:chain` з хешем транзакції.
5. Бекенд **сам** перевіряє в блокчейні, що транзакція справді існує,
   підтверджена, і справді відправлена на твою адресу — і лише тоді
   зараховує внутрішній баланс користувачу. Ніхто не може обманути систему,
   просто написавши довільну цифру в запиті.
6. Захист від подвійного зарахування: одна й та сама транзакція (`chain` +
   `txHash`) може бути зарахована лише один раз (unique constraint у БД).

### Підтримувані мережі

Навмисно тільки дві мережі — обидві працюють одразу з коробки, без реєстрації
жодного платного ключа (`src/services/deposit-verifiers/`):

- **Bitcoin** — через публічне Esplora-API (Blockstream за замовчуванням,
  можна вказати `BITCOIN_API_URL` на власний вузол).
- **Tron** (для USDT в мережі TRC20) — через TronGrid API.

EVM-мережі (Ethereum, Polygon, BSC, ...) свідомо не підключені — для них
потрібен окремий RPC-провайдер (Alchemy/Infura), а це зайва заморочка для
старту. Код для цього вже є (`EvmDepositVerifier`, `config/chains.ts`) —
якщо колись знадобиться Ethereum-депозит, достатньо додати `'ethereum'`
назад у список `KNOWN_CHAINS` в `src/api/routes/deposits.ts` і заповнити
`ETHEREUM_RPC_URL` / `ETHEREUM_TREASURY_ADDRESS` в `.env`.

⚠️ **Верифікатори Bitcoin і Tron не протестовані проти живого API** з цього
середовища (пісочниця не має виходу в інтернет) — перш ніж довіряти їм реальні
гроші, перевір на маленькій реальній транзакції на кожній мережі. Логіка
покрита юніт-тестами на змодельованих відповідях API, але не гарантує, що
форма відповіді реального Blockstream/TronGrid співпадає на 100%.

**Важливо розуміти:** у цій моделі саме твій гаманець стає єдиним сховищем
коштів усієї команди. Це нормально для довіреної команди, але означає, що
його безпека (seed-фраза, апаратний гаманець, обережність із підписанням
транзакцій) тепер критична для всіх, не тільки для тебе особисто. Немає
HSM/мультипідпису — є тільки твій ключ.

Виведення коштів (`Withdrawal`) з цієї моделі означає, що ти вручну
надсилаєш крипту зі свого гаманця користувачу і позначаєш це в системі —
або допишемо ендпоінт, який буде готувати транзакцію для підпису прямо в
гаманці (через WalletConnect/EIP-1193), якщо потрібно автоматизувати.

## Криптокартка — список очікування

Сторінка `/card` описує заплановану криптокартку (Apple Pay/Google Pay, без
комісій, кешбек 8%) — самої картки ще немає, це тільки лист очікування
(`src/api/routes/card.ts`). Приєднатись можна лише з підтвердженою
верифікацією (`kycStatus == APPROVED`) — це не наше бізнес-рішення, а вимога
будь-якого емітента карток (банк-партнер + Visa/Mastercard завжди вимагають
повний KYC власника картки, незалежно від країни реєстрації компанії).
Торгівля на біржі при цьому залишається без обов'язкового KYC — верифікація
потрібна лише для картки та майбутніх операцій з фіатом.

## API-ключі для торгових ботів

Вкладка "API" в Налаштуваннях (`src/api/routes/apiKeys.ts`) дозволяє
користувачу створити ключ і підключити власного бота/скрипт до свого
акаунта — без пароля, без JWT з браузера. Запит підписується HMAC-SHA256
(`src/api/middleware/apiKeyAuth.ts`) — секрет показується один раз при
створенні і зберігається на сервері лише в зашифрованому вигляді
(`API_KEY_ENCRYPTION_SECRET` в `.env`, `openssl rand -hex 32`). Ключ без
позначки "Дозволити торгівлю" може тільки читати баланс і ордери, не може
розміщувати чи скасовувати їх. Керувати ключами (створення/список/
відкликання) можна лише через звичайний вхід у браузері — самим API-ключем
керувати іншими ключами не можна навмисно.



```bash
npm install
cp .env.example .env   # заповнити DATABASE_URL, JWT_SECRET
npm run prisma:migrate
npm run dev
```

## Як реально розмістити це в інтернеті

Ось що ТИ маєш зробити (це неможливо автоматизувати повністю — потрібні твої
рішення: який сервер, який домен, твої ключі):

### 1. Орендуй сервер (VPS)
Наприклад Hetzner (~4-6 EUR/міс) або DigitalOcean. Обери Ubuntu 22.04,
найменший тариф вистачить для команди.

### 2. Купи домен (якщо ще немає)
Namecheap, Cloudflare Registrar — будь-що. Направ DNS A-запис на IP сервера.

### 3. Онови .env.production.example → .env
Заповни DOMAIN, паролі, і адреси свого гаманця (BITCOIN_TREASURY_ADDRESS,
TRON_TREASURY_ADDRESS) — обидві мережі працюють без реєстрації жодного
платного ключа.

### 4. На сервері
```bash
curl -fsSL https://get.docker.com | sh
scp -r crypto-exchange root@ТВІЙ_IP:/opt/exchange
cd /opt/exchange
mv .env.production.example .env   # після того як заповнив значення
docker compose up -d --build
```

Caddy сам отримає безкоштовний HTTPS-сертифікат для твого домену — нічого
вручну налаштовувати не треба. Через хвилину-дві після старту
https://exchange.твійдомен.com/health має відповісти {"status":"ok"}.

### 5. Чого ще бракує для реального використання
- Фронтенд — зараз є тільки API. Людям потрібен інтерфейс: вхід, форма
  ордера, графік, кнопка "поповнити". Скажи — і зроблю наступним кроком.
- Реєстрація/логін користувачів — ендпоінти для цього ще не написані
  (є тільки перевірка вже виданого JWT-токена).

## Реєстрація та вхід

Тепер є повноцінна автентифікація (`src/api/routes/auth.ts`), покрита 7
тестами:

- `POST /api/v1/auth/register` — email + пароль (мінімум 10 символів),
  повертає JWT-токен. Пароль хешується bcrypt (12 раундів) — у базі даних
  ніколи не зберігається як є.
- `POST /api/v1/auth/login` — email + пароль → JWT-токен на 12 годин.
  Обмежено 10 спробами за 15 хвилин з однієї IP, щоб ускладнити підбір
  пароля.
- Токен передається в усі інші запити як `Authorization: Bearer <token>`.

**Реєстрація навмисно залишається відкритою** — команда часто змінюється,
нові люди мають самі створювати акаунт без ручного втручання адміна.
Обернена сторона: будь-хто, хто отримає посилання на біржу, теж може
зареєструватися. Для приватної команди це прийнятний компроміс, але якщо
колись захочеш проміжний варіант — наприклад, реєстрація тільки з
запрошувальним кодом (без вимкнення її повністю) — скажи, це нескладно
додати поверх поточної системи.

Вимикач `REGISTRATION_OPEN=false` в `.env` все ще існує в коді на випадок,
якщо колись знадобиться тимчасово заморозити реєстрацію (наприклад, під час
інциденту) — просто він не увімкнений і не рекомендований для звичайної
роботи.

Далі за планом: простий фронтенд (форма входу, ордербук, кнопка поповнення).

## Фронтенд

Простий інтерфейс у стилі Bybit — темна тема, ордербук з барами глибини,
форма купівлі/продажу, модалка поповнення. Лежить у `frontend/`, React +
Vite + TypeScript, без важких UI-бібліотек (звичайний CSS з токенами
кольору/шрифту в `frontend/src/index.css`).

### Запуск локально
```bash
cd frontend
npm install
npm run dev   # http://localhost:5173, проксіює /api на бекенд localhost:3000
```

### У продакшені
`docker-compose.yml` вже включає фронтенд-контейнер (nginx, роздає зібраний
білд) — після `docker compose up -d --build` на сервері Caddy сам направляє
`/api/*` на бекенд, а решту шляхів — на фронтенд, під одним доменом.

Що вже працює в інтерфейсі: реєстрація/вхід, перегляд ордербуку (оновлюється
кожні 2 секунди), розміщення лімітних ордерів купівлі/продажу, поповнення
через адресу-скарбничку з перевіркою хеша транзакції, графік ціни (свічки,
`lightweight-charts` — безкоштовна бібліотека TradingView, не плутати з
їхньою платною Charting Library) з перемиканням таймфрейму 1m/5m/15m/1h/4h/1d,
оновлюється кожні 5 секунд.

Графік будується з реальних угод через новий бекенд-ендпоінт
`GET /api/v1/candles/:pair` (`src/services/CandleService.ts`, покритий
тестами) — групує угоди у свічки OHLC на льоту. Поки що це рахується в
коді при кожному запиті; якщо навантаження сильно зросте, варто перенести
агрегацію у фонову задачу чи матеріалізоване представлення в базі — про це
є нотатка прямо в коді сервісу.

Чого ще нема: список власних відкритих ордерів і балансів на екрані (API
для цього вже є частково — треба дописати ще один `GET`-ендпоінт), вибір
торгової пари (зараз захардкоджено BTC/USDT).

## Відновлення ордербуку після рестарту

Matching engine тримає активні ордери в пам'яті процесу — швидко, але
означає, що будь-який рестарт сервера (деплой, оновлення, збій) очищав би
їх без сліду. Тепер це виправлено: `src/services/OrderBookRecovery.ts`
підвантажує всі ордери зі статусом OPEN/PARTIALLY_FILLED з бази даних назад
у matching engine одразу при старті сервера, ще ДО того, як він почне
приймати запити — і робить це у правильному хронологічному порядку, щоб не
зламати черговість виконання (price-time priority) серед ордерів з
однаковою ціною. Покрито тестами, включно з перевіркою, що черговість
справді зберігається.

## Виведення коштів — поки що НЕ реалізовано

Наразі це особиста тестова біржа (гроші команди ще не заведені), тому це
відкладено свідомо. Коли дійде до реальних коштів команди — знадобиться
API-ендпоінт для запиту на виведення плюс ручне підтвердження й відправка з
MetaMask (архітектура для цього вже описана в `WalletService.ts`).

## Товари/послуги + внутрішній баланс (платіжний сервіс)

Тепер поверх торгівлі є другий режим використання: продаж твоїх власних
товарів чи послуг за внутрішній баланс. Логіка:

1. Людина реєструється, поповнює крипту (та ж адреса-скарбничка — твій
   MetaMask, той самий механізм, що й для торгівлі).
2. У неї з'являється внутрішній баланс — видно в навбарі зверху.
3. На сторінці `/products` вона бачить твій каталог і натискає "Купити".
4. Баланс автоматично списується (`src/services/PurchaseService.ts`,
   покритий 5 тестами) — це внутрішня бухгалтерська операція, жодного
   блокчейну тут немає, бо реальна крипта вже давно на твоєму MetaMask.
5. Створюється запис `Purchase` зі статусом `PENDING_FULFILLMENT` — **ти
   вручну** надаєш товар/доступ і позначаєш замовлення виконаним (це вже
   робота для інтерфейсу адміна, поки що можна робити прямо через базу
   даних або дописати екран для цього, скажи, якщо треба).

### Як додавати товари (тільки ти можеш)

Функціонал захищений через `isAdmin` на акаунті — жодної кнопки
"стати адміном" немає навмисно. Зроби себе адміном прямо в базі даних
одразу після деплою:

```sql
UPDATE "User" SET "isAdmin" = true WHERE email = 'твій@email.com';
```

Після цього можеш додавати товари через API:
```bash
curl -X POST https://твійдомен.com/api/v1/products \
  -H "Authorization: Bearer ТВІЙ_ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '{"name":"Консультація 1 год","description":"...","priceAmount":"50","priceAsset":"USDT"}'
```

Інтерфейсу для додавання товарів через кнопки в браузері поки нема — тільки
через API. Скажи, якщо хочеш просту адмін-панель для цього.

## Швидкий безкоштовний деплой (Render + Neon)

Для першого тестового запуску — щоб просто побачити, як біржа виглядає в
інтернеті, без оренди сервера. Мінуси такого варіанту: сайт "засинає" через
15 хв без відвідувань і прокидається 30-50 сек при першому заході — для
серйозного використання команди варто перейти на VPS (розділ вище), але для
"показати й перевірити" цього більш ніж достатньо.

### 1. Завантаж код на GitHub
Створи безкоштовний акаунт на github.com → New repository → на сторінці
репозиторію просто перетягни туди всі файли й папки з розпакованого архіву
(крім `node_modules` і `frontend/node_modules`, якщо вони раптом
згенерувались — їх там бути не повинно) → Commit. Це можна зробити прямо в
браузері, без встановлення git.

### 2. База даних — Neon
neon.tech → New Project → скопіюй "Connection string" (виглядає як
`postgresql://user:pass@ep-xxx.neon.tech/dbname?sslmode=require`).

### 3. Бекенд — Render
render.com → New → Blueprint → підключи свій GitHub-репозиторій. Render сам
побачить файл `render.yaml` у корені і запропонує створити два сервіси
(`exchange-api` і `exchange-frontend`). Перед стартом він попросить вручну
заповнити позначені як "sync: false" значення:
- `DATABASE_URL` — рядок з Neon (крок 2)
- `ALLOWED_ORIGINS` — поки залиш порожнім, повернешся сюди після кроку 4

`JWT_SECRET` Render згенерує сам.

### 4. Фронтенд
Другий сервіс (`exchange-frontend`) Render теж створить автоматично з того
самого репозиторію. Йому потрібно вказати `VITE_API_URL` — це адреса
бекенда з Render (буде видно в дашборді після деплою `exchange-api`,
виглядає як `https://exchange-api-xxxx.onrender.com`) + `/api/v1` в кінці.

### 5. Заверши налаштування
Коли фронтенд задеплоївся і ти бачиш його адресу (щось на кшталт
`https://exchange-frontend-xxxx.onrender.com`) — повернись до сервісу
`exchange-api` в Render, постав цю адресу в `ALLOWED_ORIGINS`, збережи —
Render сам передеплоїть.

Відкрий адресу фронтенду в браузері — ось і твоя біржа, доступна будь-кому
в інтернеті за посиланням.

⚠️ Депозити (поповнення через власний гаманець) на цьому етапі можна не
налаштовувати — `BITCOIN_*` / `TRON_*` змінні необов'язкові, без них просто
не працюватиме модалка "Поповнення" (список мереж буде порожній), решта
функцій (реєстрація, торгівля, товари) працюватиме нормально.
