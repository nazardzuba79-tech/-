| **DNS-over-HTTPS** | запись HTTPS (type 65), ECH-конфиги | — |

**Чего доказать НЕЛЬЗЯ имеющимися средствами:**

1. **Реальный браузер из России.** Ни один доступный инструмент не запускает Chrome/Firefox на абонентской линии в РФ.
2. **Отказ по ECH в принципе невидим для curl-подобных пробников** — они не отправляют расширение ECH. Это отдельно зафиксировано OONI: их стандартные тесты связности этот блок не детектируют. Поэтому «200 OK» от всех пробников **не является** доказательством того, что сайт открывается у людей.

Это главная причина, по которой ниже строго разделены «доказано» и «вероятно».

## 2. Что доказано

Всё ниже — собственные замеры этой сессии, воспроизводимые.

**2.1. VOLTEX целиком стоит на Cloudflare, включая API.**
`voltextech.net`, `www.voltextech.net` и `api.voltextech.net` резолвятся в одни и те же free-tier anycast-адреса `104.21.29.149` / `172.67.149.103`. На `api.voltextech.net` заголовки `server: cloudflare`, `cf-ray`, `cf-cache-status: DYNAMIC`, а `x-render-origin-server: Render` — это origin. То есть API **не** смотрит напрямую в Render, он тоже за Cloudflare.

**2.2. Все три хоста публикуют ECH — и это ровно та сигнатура, которую блокирует ТСПУ.**
DNS-запись HTTPS (type 65) содержит:

```
ech=AEX+DQBBBQAgACCVAfv+eX8xSPjHUH7jeS+MihjJy0VOFrcPD5DxzuO9EwAEAAEAAQASY2xvdWRmbGFyZS1lY2guY29tAAA=
```

Расшифровка: версия `0xfe0d`, **public_name = `cloudflare-ech.com`**.
Публично описанная сигнатура блокировки требует одновременно ECH-расширения **и** SNI `cloudflare-ech.com`. Совпадение точное.

**2.3. Российские резолверы эту запись отдают без изменений.**
Проверено на резолверах МТС, Ростелекома, ЭР-Телекома, PortTelekom и таганрогского кооператива — все возвращают `ech=`. Значит браузер абонента её получит и попытается ECH-хендшейк.

**2.4. Больше ни один хост из зависимостей VOLTEX ECH не анонсирует.**
`ws.kraken.com`, `api.bybit.com`, `stream.bybit.com`, `cdn.jsdelivr.net`, `fonts.googleapis.com`, `onrender.com` — ни у одного нет `ech=`. VOLTEX здесь единственный.

**2.5. Bybit для России стоит на принципиально другой инфраструктуре.**

| | VOLTEX | Bybit Global |
|---|---|---|
| Веб | Cloudflare Pages | **Tencent EdgeOne** (`eo.dnse4.com`) |
| API / stream | Cloudflare → Render Oregon | **Akamai** (`edgekey.net`) |
| IP для РФ | CF anycast, ближайший PoP вне РФ | **Akamai-узлы внутри РФ** (`95.100.107.171`) |
| ECH | **есть** | **нет** |

**Контракт кэширования в `_headers` для неё не применяется.** Продакшен отдаёт `/` → `no-cache` и `/assets/*` → `immutable` корректно, но `/hero/*.png` приходит с `cache-control: max-age=14400` вместо объявленного в `/*` правила `no-cache`. То есть заявленный в файле контракт и фактически отдаваемый — разные, и повторный визит перекачивает 1,85 МБ каждые 4 часа.

**2.8. Fallback фьючерсного стакана сломан в продакшене — и это не про Россию.**

```
GET /api/v1/market/futures/orderbook/BTCUSDT
{"available":false,"reason":"provider_unavailable",
 "detail":"Failed to reach bybit: Direct Bybit access disabled in API region"}
```

`exchange-api` живёт в **Oregon (США)**, Bybit не обслуживает США. Резервный путь для стакана не может работать **ни для кого** и **никогда** — независимо от блокировок. Если браузерный `wss://stream.bybit.com` не поднимется, у фьючерсного стакана не остаётся ни одного источника.

**2.9. Что настроено правильно** (проверено, проблемой не является): CORS отдаёт `access-control-allow-origin` и для apex, и для `www`; `VITE_API_URL` вшит верно — `https://api.voltextech.net/api/v1`; Google Fonts подключены неблокирующе; `_headers` корректен; SSE ставит `X-Accel-Buffering: no` и heartbeat 15 с.

**2.10. В центральном API-клиенте нет таймаута.** `frontend/src/lib/api.ts:503` — `request()` вызывает `fetch` без `AbortController` и без `signal`. На зависшем соединении запрос висит до дефолта браузера (минуты), ошибка пользователю не показывается.

## 3. Что вероятно, но мной не доказано

1. **Блокировка ECH применяется к VOLTEX прямо сейчас.** Сигнатура совпадает точно (§2.2), запись доезжает до абонентов (§2.3), но проверить это можно только настоящим браузером на абонентской линии. Механизм по публичным описаниям — **отбрасывание пакетов**, не RST: соединение просто виснет, Firefox повторяет без ECH примерно через минуту.
2. **Троттлинг Cloudflare как объяснение §2.6.** Cloudflare публично заявляла об ограничении с 9 июня 2025 у Ростелекома, МегаФона, ВымпелКома, МТС и МГТС и называла цифру «первые 16 КБ». Мой замер даёт границу 62–206 КБ — то есть явление наблюдается, но численно с публичной цифрой не совпадает; вероятно, политика различается по операторам и во времени.
3. **Масштаб.** Отказ воспроизвёлся на **1 из 3** доступных точек. Обе прошедшие ноды — хостинг AS210644. Доля затронутых абонентов из этого не выводится.
4. **Render free засыпает.** `/health` показывал аптайм 17 минут в момент проверки; free-план Render усыпляет сервис после простоя. Это добавляет десятки секунд к первому запросу — но отдельно я это не воспроизводил.
5. **Холодный старт Render выглядит как ошибка CORS, а не как медленный ответ.** Пока сервис просыпается, Render отдаёт свою HTML-заглушку, на которой нет заголовка `Access-Control-Allow-Origin`. Браузер в этом случае сообщает не «долго», а «ошибка CORS» — то есть первый посетитель после паузы получает вид полностью сломанного приложения. Активно не проверял: воспроизведение требует дождаться усыпления продакшена.
6. **Счётчик лимита запросов может считать не по пользователю.** В `src/index.ts:180` стоит `app.set('trust proxy', 1)`, но до приложения два прокси-хопа — Cloudflare и Render. Если ключом окажется egress-IP Cloudflare, то все пользователи, выходящие через один и тот же PoP, делят общий лимит 120 запросов в минуту. Российские пользователи как раз сходятся в небольшое число PoP. **Намеренно не проверял активно** — проверка означала бы расход реального лимита на продакшене и могла бы задеть живых пользователей.
7. **Собственные таймауты клиента срабатывают раньше ответа.** Отдельные экраны ставят прерывание на 9–15 с (например `CfdChart.tsx:78` — 9 с), а холодный `/market/external/tickers` отвечал 13,4 с даже из США. С российской задержкой сверху эти прерывания срабатывают штатно, и пользователь видит «не загрузилось» при живом сервере.

## 4. Что работает нормально

DNS во всех проверенных российских сетях. TCP/443 и TLS-хендшейк ко всем хостам. HTTP для не-ECH клиентов. Латентность приемлемая: 43–163 мс до фронтенда, 252–347 мс до API. CORS. Сборка и вшитый `VITE_API_URL`. Мелкие API-ответы (`/market/global` — 234 Б). Cloudflare-адреса VOLTEX **не** заблокированы по IP: МТС, Ростелеком, Билайн и ЭР-Телеком открывают их штатно.

**Ни один сторонний хост, к которому обращается браузер, из России не заблокирован.** Проверено отдельно, коды ответа — прикладные, а не признак блокировки:

## 5. Где именно ломается

Два независимых механизма, оба — на **Cloudflare-участке**, и оба до того, как запрос дойдёт до Render или Neon.

**Механизм A — ECH.** Браузер получает `ech=` из DNS → шлёт ClientHello с ECH и SNI `cloudflare-ech.com` → ТСПУ отбрасывает пакеты → сайт «висит и не открывается». Для curl и пробников невидимо, потому что они ECH не шлют.

**Механизм B — обрыв крупных тел.** Соединение устанавливается, TLS проходит, мелкое проходит, крупное виснет. Практически для VOLTEX:

```
index.html   4 КБ   → доезжает, браузер рисует пустой <div id="root">
index.js   168 КБ   → зависает  ⟹  приложение НЕ СТАРТУЕТ
```

Это и есть «белый экран». Причём brotli-поток, оборванный на середине, не декодируется **вообще** — то есть не «часть приложения», а ничего.

Механизм B бьёт и по API с того же адреса: `rankings` (1,06 МБ), `tickers` (91 КБ) и первый кадр SSE (908 КБ) — все далеко за границей.

**Усилители (не причины):**

- нет таймаута в `api.ts:503` → вместо ошибки вечный спиннер;
- SSE при каждом разрыве перезапрашивает те же 908 КБ по кругу;
- сломанный fallback фьючерсного стакана (§2.8) убирает единственный запасной путь;
- hero-картинка 1,85 МБ забивает и без того узкий канал на главной;
- холодная `/futures` требует 13 отдельных запросов за JS-чанками — байт немного (373 КБ br), но это 12 последовательных round trip'ов по 300–600 мс каждый;
- нет service worker и офлайн-кэша: ни одного визита нельзя пережить без живого обращения к Cloudflare;
- упавший ленивый чанк даёт один тихий перезагруз страницы, а со второго раза — карточку ошибки.

**Чего в списке причин нет:** Render как таковой, регион Oregon, Neon, WebSocket-провайдеры, DNS, сертификаты, CORS и сборка. Frontend и API ломаются **одинаково и по одной причине**, потому что стоят за одним и тем же Cloudflare.

## 6. Нужен ли второй домен

**Сам по себе — нет. Второй домен на Cloudflare не изменит ничего.**

Блокируются не имена, а (A) TLS-признак ECH и (B) сетевой путь Cloudflare. Новый домен, заведённый в Cloudflare, получит **ту же** автоматическую запись `ech=` с тем же `cloudflare-ech.com` и **те же** anycast-адреса. Ни один из двух механизмов не обойдётся.

**Bybit'у помог не второй домен, а другой CDN.** `bybitglobal.com` — это Tencent EdgeOne для веба и Akamai для API/stream, с узлами **внутри России**. Имя поменялось заодно; работает — смена инфраструктуры.

**Когда второй домен всё же осмыслен:** только как носитель другой инфраструктуры — если на него ставится не-Cloudflare CDN, а основной домен остаётся как есть для остального мира. Тогда решает по-прежнему CDN, а домен лишь позволяет не трогать текущий прод.

| **Deploy** | не нужен |
| **Откат** | мгновенный, обратная настройка |
| **Что решает** | механизм **A**. Механизм **B** — **нет** |

Дёшево и безопасно, но само по себе может не вернуть доступ, потому что крупные файлы продолжит обрывать.

### Вариант 2. Увести `api.voltextech.net` с Cloudflare-прокси на прямой Render

| | |
|---|---|
| **Что меняем** | одну DNS-запись: «серое облако» / CNAME прямо на Render. Ноль кода |
| **Риск** | средний: раскрывается origin, теряются Cloudflare-кэш и защита от DDoS; Render free при этом принимает трафик напрямую |
| **Стоимость** | $0 |
| **Neon** | нет влияния — запросов не прибавляется |
| **WebSocket** | нет влияния; SSE начинает ходить мимо Cloudflare |
| **Скорость** | вероятно **медленнее**: пропадает edge-терминация, каждый запрос идёт в Oregon целиком |
| **Deploy** | не нужен, только DNS |
| **Откат** | возврат записи, минуты |
| **Что решает** | A и B **для API** (`onrender.com` ECH не анонсирует). Для фронтенда — **нет** |

Важно: Cloudflare Pages всегда проксируется, «серое облако» на нём невозможно. То есть фронтенд этим вариантом не лечится.

### Вариант 3. Перенести отдачу статики с Cloudflare Pages на CDN, который в России не ограничивают

| | |
|---|---|
| **Что меняем** | хостинг статики + DNS. Код приложения не трогается, меняется только цель деплоя |
| **Куда** | это путь Bybit. Кандидаты — Selectel / Yandex Cloud CDN / VK Cloud / EdgeCenter / NGENIX или иной не-Cloudflare edge |
| **Риск** | наибольший из трёх: новый пайплайн деплоя, TLS-сертификаты, проверка кэш-контракта `_headers` на новой платформе |
| **Стоимость** | от небольшой до заметной, зависит от провайдера; российские CDN дороже и покрывают не весь функционал Cloudflare |
| **Neon** | нет влияния |
| **WebSocket** | нет влияния |
| **Скорость** | для РФ — быстрее; для остального мира может ухудшиться, если у провайдера нет глобальных PoP |
| **Deploy** | да, новый пайплайн |
| **Откат** | возврат DNS на Pages, но после настройки и прогрева — то есть не мгновенно |
| **Что решает** | A и B **для фронтенда** — то есть собственно «белый экран» |

### Рекомендуемая последовательность

1. **Сначала Вариант 1** — он почти бесплатен, обратим и снимает механизм A. Если после него доступ вернулся, механизм B на этих сетях не критичен, и дальше идти не нужно.
2. **Если нет — Вариант 3** для фронтенда, при необходимости с Вариантом 2 для API.
3. **Независимо от блокировок** имеет смысл починить §2.8 (стакан фьючерсов сломан для всех) и §2.10 (нет таймаутов), а также сократить первый кадр SSE и `rankings`: 908 КБ и 1,06 МБ тяжелы на любой сети и увеличивают шанс попасть под ограничение. Это изменения в коде и в эту задачу не входили.

## 8. Как проверить вывод за 2 минуты

Нужен человек в России без VPN:

1. Открыть `https://voltextech.net` в Chrome → F12 → Network. Если `index.html` = 200, а `/assets/index-*.js` висит в `(pending)` и потом падает — **механизм B подтверждён**.
2. В Firefox открыть `about:config`, поставить `network.dns.echconfig.enabled = false` и `network.dns.http3_echconfig.enabled = false`, перезапустить, открыть сайт снова. Если после этого открывается, а до — нет, **механизм A подтверждён**.

Эти две проверки закрывают ровно то, что я доказать не смог.
