# Stocks native stream transport assessment — 2026-10-13

Research only. No WebSocket connection, provider test request, implementation, deployment, or paid service was used. Official documentation was read through web browsing. Local source inspected: PR512 baseline `cbd08c8f4a7de2ed0987a48d0ad1f84563d6c0f1` plus the separately reviewed Wallet-only FX working changes. Evidence: `DEMAND-REPORT.md`, `summary.json`, existing MarketHub/server/engine code.

**Conclusion:** more hardware cannot fix the measured REST request-count constraint. The documented workload floor is conditional: 13 Binance symbols × 7 quote waves + 13 × 3 initially requested timeframes = 130 starts within the scenario, exceeding the unchanged 100-start/60-second local ceiling before ticker, FX, retries or repeated mutable-window requests. A shared public stream changes that demand model; it does not prove CPU capacity, source availability, or redistribution rights.

## Smallest useful boundary

Add an optional Stocks-only public-data adapter under MarketHub, initially disabled, while retaining its current quote/history return contracts. Start with native trade snapshots; retain budgeted REST bootstrap/history and existing dual-currency conversion. Add provider-native kline and display-ticker subscriptions separately after identity/correction tests. Do not add a broker/order client, touch Spot/Futures, or send provider messages from ledger code.

Binance documents raw `<symbol>@trade` with trade ID `t`, trade time `T` and price `p`; UTC klines contain `t`, interval, OHLCV and finality `x`; symbol ticker streams provide rolling statistics. The raw trade feed is the relevant execution-source candidate, rather than aggregate trades, book ticker, statistics or candle close. [Official stream schemas](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-streams/~).

Use the exact catalogued provider/symbol. Preserve the current Binance last-trade normalization: bid/ask/last from that trade price, event identity from the native trade ID, timestamp from native trade time, and the existing simulated capacity. Keep arrival time separate. Reject malformed, unsafe-integer or wrong-symbol identities rather than rounding them; any lossless ID parser must preserve compatibility with existing durable event keys.

**A stream callback must update only a public read model.** Feeding every received trade directly into account observations would increase matching opportunities and change financial behavior. Existing authenticated demand, account worker, owner authorization, observation cadence, event-capacity reuse, recovery and commit rules remain the only route into matching. Intermediate streamed events need not be replayed into accounts. Switching transport can still alter which valid latest event is observed at a given wall-clock instant; equivalence is established for identical input events, not by promising identical live fills across two asynchronous transports.

## Demand and bounds

Maintain one shared provider connection and reference-counted active symbol/timeframe subscriptions. Viewer data interest must be distinct from the owner's execution lease: current read-only viewers do not acquire that execution lease. A Wallet snapshot remains a bounded request, never an indefinite position-driven subscription. Release data interest on view switch, hide/unmount/logout, disconnect or lease expiry. After the final interest, cancel retries and close the socket; no reconnect timer survives an empty demand set.

Use explicit frame, active-symbol, timeframe, retained-byte and pending-control bounds. Reuse the existing history memory budget instead of an unbounded parallel candle store. Do not subscribe to all-market feeds. Keep only the latest eligible quote and provider candle versions required by active readers; do not write every tick to SQLite or disk. If parsing falls behind, close/fence and reconcile rather than accepting silent data loss. Bounds need measured sizing; no 100-user guarantee follows from one connection.

Binance specifies 24-hour connection lifetime, ping every 20 seconds, matching pong within one minute, five incoming control/ping/pong messages per second, 1,024 streams per connection and 300 connection attempts per five minutes per IP. [Official connection rules](https://github.com/binance/binance-spot-api-docs/blob/master/web-socket-streams.md#general-wss-information). Batch only demanded subscribe/unsubscribe changes, reserve heartbeat capacity, acknowledge control requests, and use bounded jittered reconnect/backoff. A successful subscription acknowledgement is not fresh price evidence.

## Bootstrap, disconnects and correctness

Use explicit states such as OFF, CONNECTING, SYNCING, READY and UNAVAILABLE, with a generation fence. Validate metadata and start buffering bounded native messages before a coalesced REST snapshot; reconcile overlapping IDs/timestamps before publishing READY. Do not assume undocumented consecutive trade IDs prove complete delivery. Duplicate/out-of-order events must not regress the last admitted event or reset used capacity. Old connection callbacks cannot revive a newer or released generation.

On connection failure, malformed events, buffer overflow or uncertain continuity, fence execution admission immediately. An old display value may retain its actual age, but reception of a ping must never refresh a trade's age. Preserve current quote/FX age checks; do not stamp old native trades with the reconnect time. Recovery requires validated source observations and the existing account recovery/visible-demand fences. Do not replay gap backfill into limit matching or retroactively change fills. If the existing failure path cannot promptly invalidate previously admitted account observations, that is an implementation blocker requiring explicit regression proof before enabling the adapter.

Bootstrap/reconcile candles through normal `/api/v3/klines`, keyed by symbol, interval and open time. Binance REST defines native klines by open time and exposes one-symbol recent trades separately. [Official REST contracts](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market). Use provider OHLCV as received, not reconstructed candles from sampled trades. Do not add cumulative volume on each update. Respect UTC interval boundaries and actual missing bars. A final candle flag does not establish permanent immutability: reconcile overlapping history after reconnect and invalidate affected cached ranges/serialized responses on verified corrections. Conflicting equal-version payloads need reconciliation, not arbitrary last-write wins.

Keep every REST bootstrap, fallback, metadata, FX and correction call behind the existing shared 100-start budget and singleflight paths. Separate metrics must expose socket messages/reconnects and REST starts. No host rotation, per-user fallback storms, polling during a healthy stream, or queue extension. Actual provider weighted limits also apply: Binance uses IP-based weights and requires backoff on 429/418 with Retry-After. [Official REST limits](https://developers.binance.com/en/docs/products/spot/rest-api#limits). These limits are distinct from our stricter local start ceiling. Do not move repeated REST-style requests to the WebSocket request API and call that a stream optimization.

## Required proof before activation

- Offline native fixtures: exact REST/stream mapping, non-parity FX, unsafe IDs, wrong symbols, stale/future times, duplicates, reordered messages and conflicting payloads.
- Same-event USDT/USDC shared capacity; legacy USDC limits and valuation; no unsolicited fills from feed callbacks; Alice/Bob isolation; recovery, idempotency and FULL commit-before-ack unchanged.
- Socket generation/heartbeat/shutdown/reconnect tests; held bootstrap plus active hide/switch/abort; no late reactivation; zero subscribers means zero sockets/retries/source reads.
- Native candle bootstrap overlap, mutable and closed corrections, gaps, UTC boundaries, timeframe changes, cumulative-volume replacement and history serialization invalidation.
- Disconnect/overflow storms with strict total REST budget, weighted-limit backoff, bounded RAM/queues and explicit unavailable responses. A timeout must not cause duplicate fallback requests.
- Repeat original capacity/coexistence matrices with the new transport fixture and unchanged criteria, retaining the REST baseline. Fixtures alone cannot establish real-feed availability or hardware headroom.

A safe incremental implementation is possible within Stocks, without changing financial calculations, but it is a transport/lifecycle project rather than a one-line cache fix. Real symbol availability on this exact Spot stream, native correction behavior, observed delivery latency/message rate, reconnect behavior, regional access and commercial usage permission remain unverified. Binance's separate Stocks Trading API documentation is not evidence that the existing bStock symbols are available on the chosen Spot stream. MOEX stays blocked. No production readiness, server-size recommendation or redistribution permission is established here.
