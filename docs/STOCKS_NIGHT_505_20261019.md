## CPU/HTTP diagnostic implementation

Harness-only `cpu-http-profile.cjs` defaults off. Explicit start collects per-process
CPU sampling through a local inspector Session (no inspector TCP port), CPU usage,
GC, event-loop delay/utilization and sanitized Undici/server events. API worker has
single-use diagnostic-only `profile-start` / `profile-stop` IPC commands.
`profile-session.cjs` wraps an existing caller's operation for API and generator
capture and cleans up on success/failure. It does not launch or schedule workload.

Bounds: 20,000 events, 45-second cooperative deadline, 1000-us sampling interval,
20,000 exported CPU nodes and 60,000 exported samples. Truncation counters are
explicit. A blocked JS event loop can delay the deadline; this is not a hard OS
memory quota or preemption guarantee. Hooks/subscriptions/listeners are restored.
No request/response bodies, raw URLs, query strings, headers, bearer tokens, DSNs,
account IDs, arbitrary error messages or absolute filesystem paths are exported.
Only strict harness correlation IDs and allowlisted route classes survive.

`profile-summary.cjs` reports same-process matched create→send, send→headers,
headers→trailers and callback→finish distributions, connection reuse and CPU
sample categories. Missing/truncated intervals remain incomplete. It does not
subtract independent percentiles or claim cross-process clock precision. Wall/monotonic
anchors and drift are captured; cross-process uncertainty remains unmeasured.
PostgreSQL/Prisma native-engine CPU is **not** measured by a V8 profile. Sample
categories are hints; raw source line/column frames are needed for attribution.

Existing spans still supply JWT/JSON wall spans, Prisma engine/query/transaction
observations and aggregate PG wait samples. They are not exclusive CPU timers and
cannot prove a pure pool wait or absence of locks. Instrumentation overhead needs
an off/on comparison in a future authorized environment before acceptance use.

Old runners/policies and historical FAIL reports are unchanged. In particular,
the ce670-pinned runner must reject this changed runtime as `RUNTIME_SOURCE_CHANGED`.
Do not widen admission or label the new code ce670. A later approved experiment
needs an explicit reviewed candidate pin, then may use `withProfiles` around its
unchanged driver window. No load runner was executed this shift.
