# VOLTEX: запас ресурсов перед акциями и индексами

**Вывод: нужны конкретные ограничения до интеграции.** Объём истории 250 инструментов и отдельный сборщик помещаются в проверенный бюджет. Утверждение «без ухудшения Spot/Futures» не подтверждено: на изолированном стенде совместная загрузка истории и чтение графиков увеличили p95 криптоопераций примерно на **36%**, p99 — на **49%**. Ошибок торговых операций не было, но возникали задержки начала обработки. Production оставлен без изменений; merge/deploy не выполнялись.

Проверенный main и действующий API: `3e64ae89e4b328dfc3577e0539301c20ee07b31e`. Fresh-fetch выполнен до обследования. Исследование — 2026-10-07. Короткое наблюдение Hetzner: **13:38:53–13:44:04 UTC, 310.6 секунды, 31 снимок**. История sysstat: **143 примерно десятиминутных записи за последние сутки**, с 2026-10-06 13:40:31 до 2026-10-07 13:40:06 UTC. Десятиминутные максимумы не являются мгновенными пиками.

**Указанные владельцем 40 ГБ — это диск, не RAM и не размер БД.** Фактическое блочное устройство `/dev/sda`: 40,961,572,864 байта; корневая файловая система: 39,956,590,592 байта. Различие GB/GiB и размер служебных разделов учтены.

**Основная база расположена на том же Hetzner**, PostgreSQL 18.6 в `voltex-cutover-db-1`, Docker volume `voltex-cutover_pg18`, host path `/var/lib/docker/volumes/voltex-cutover_pg18/_data`; каталог данных версии 18 — `18/docker`. Это не Render/Neon. Название существующей production database — `voltex_stage`; название не означает, что её можно использовать для тестов.

**Свободно 14.51 GB / 13.51 GiB на корневой файловой системе.** Предлагаемая история акций при размещении отдельного SQLite-каталога на этом VPS заняла бы место **на том же физическом диске**, даже вне финансовой БД. Сейчас тестовые файлы находятся только на локальном Windows SSD.

API `index.js` и `marketDataCollector.js` — отдельные Node-процессы **в одном** контейнере `voltex-cutover-api-production-1`. У контейнера memory ceiling 1,500 MiB, у PostgreSQL — 1,600 MiB; у обоих нет CPU quota, PIDs limit 256. MemorySwap limits заданы, но swap на хосте равен нулю, поэтому запаса swap нет. Пятиминутные средние: API-процесс 0.029 vCPU, коллектор 0.149 vCPU, PG-контейнер 0.024 vCPU. Максимальный RSS API 344.02 MiB, коллектора 134.54 MiB; память PG cgroup максимум 522.47 MiB. RSS отдельных PostgreSQL workers суммировать как уникальную память нельзя.

Локальные production backups: `/backups` 467,820,176 байт и `/offsite` 471,423,333 байта, вместе около 896 MiB. Журнал ОС — 104 MiB; API log около 0.85 MiB, PostgreSQL local-driver logs 337,511 байт. Это текущий размер, не скорость их роста. За короткий замер swap activity и прирост kernel OOM counter равны нулю; совпадений kernel OOM за сутки не найдено. Start time контейнеров до/после одинаков, RestartCount 0; это не полная история всех замен контейнеров за сутки.

## Стенд и проверенный объём

**ИЗМЕРЕНО.** Windows, Intel Core Ultra 9 275HX, 24 логических CPU, около 63.44 GiB видимой RAM, локальный NVMe SSD/NTFS. Это иной CPU, диск и ОС, чем production Xeon/Linux. Для сравнения криптоопераций все дочерние процессы закреплены за одними двумя логическими CPU; физическая эквивалентность Hetzner этим не достигается. PostgreSQL стенда 18.4, loopback, shared_buffers 64 MB, max_connections 20, Prisma pool limit 8. Production PostgreSQL 18.6/max_connections 100. Рабочие production данные не копировались.

Данные свечей **синтетические**. Объём соответствует 100 US + 50 RU + 100 Asia; 100 Asia не является утверждённым каталогом. Формат: `(symbol, timestamp, open, high, low, close, volume)`, `WITHOUT ROWID`, первичный ключ `(symbol,timestamp)`, отдельная таблица latest на 250 инструментов. Это схема для измерения, без окончательного каталога/валют/корпоративных действий. Собирается готовая закрытая OHLCV-свеча; OHLC не восстанавливается из редких цен. Проверяется признак closed, время закрытия, конечность чисел и OHLC-инварианты.

- 250 × 32 × 22 = **176,000 свечей** за модельный месяц: 10.999 с, 9.613 MiB. Candles B-tree 10,072,064 байта; latest и schema по 4,096 байт. Ключ встроен в B-tree, поэтому нет отдельного файла secondary index.
- **2,112,000 свечей** за 12 модельных месяцев: 120.850 с, 115.250 MiB. Candles B-tree 120,840,192 байта; latest/schema ещё 8,192 байта. Получилось примерно **57.22 байта на свечу** в этом формате, не принятое заранее предположение 200 байт.
- Во время записи месяц: main 9,826,304 + WAL 1,116,552 + SHM 32,768 байт. Год: main 120,451,072 + WAL 1,128,912 + SHM 32,768 байт. WAL частично дублирует страницы main; его нельзя считать дополнительными уникальными свечами. После закрытия соединений журнал checkpoint-ится в main.
- Регулярный цикл: ровно **250 новых строк**, 1.544 с, 0.28125 CPU-seconds после установки лимита; без ошибок. Параллельность запросов 4, запись истории пакетами до 500 строк; массив всей истории не создаётся. Следующий цикл начинается после завершения предыдущего.
- Жёсткий Windows Job Object cap 0.1992 vCPU и 256 MiB private memory успешно применён. Годовой прогон потребил 0.196 vCPU в среднем, пик RSS 34.76 MiB. Лимит не является утверждением о такой же скорости на Xeon.

**РАСЧЁТ.** При одном запросе на инструмент за полный интервал: максимум 250 запросов за 15 минут, в среднем 0.278 запроса/с, 16.67/мин при полном пересечении сессий. При 22 условных восьмичасовых сессиях — 176,000 свечей/месяц. Это не расписание реальных бирж и не число кредитов конкретного провайдера: batch-запрос может тарифицироваться за каждый symbol.

Внешнее тестирование чтения: общий cache 64 entries/15 s, максимум 1,000 свечей в ответе, популярный набор 10 инструментов. При 10/50/100 одновременно читающих клиентах соответственно: **1,560 / 1,744 / 1,581 запрос**, p50 **17.36 / 171.88 / 352.45 ms**, p95 **38.06 / 290.04 / 659.79 ms**, p99 **45.48 / 362.71 / 784.46 ms**, ошибок 0. Каждый сценарий длится около 8 секунд. Cache: 4,865 hits, 20 misses, 10 заполненных entries. Рост задержек при 100 клиентах показывает предел конкретного минимального threaded-сервера/генератора; это не готовый production API.

## Влияние на существующие Spot/Futures

Использованы **неизменённые реальные сервисы проекта** `OrderService`, `FuturesPositionService`, `FuturesProtectionService` и настоящие транзакции новой PostgreSQL. Проверены чтение состояния, Spot create/cancel/fill, Futures create/cancel/open/manual close, установка/чтение TP/SL, sweep и фактическое срабатывание TP и SL. Два синтетических аккаунта с одинаковыми начальными данными, фиксированные цены/ликвидность. В каждом из A/B/C/D — 3 повторения по 20 секунд, 80 циклов, 14 измеряемых service calls на цикл, одинаковые лимиты и warm-up. Порядок перемешан: A B C D / D C B A / B D A C.

Итоговая пропускная способность сохраняется за счёт последующего догоняющего выполнения; это не означает отсутствия задержек.

Дополнительный одиночный ресурсный прогон каждого сценария отделён от основного сравнения. PG CPU: A 0.111, B 0.096, C 0.103, D 0.118 vCPU в среднем; максимум односекундного PG-интервала 0.199 vCPU. Суммарная средняя загрузка всех учитываемых процессов C около 1.74 из 2 логических CPU. Она включает локальный fixture-провайдер и генератор читателей, которые в production могли бы находиться вне VPS. Логические записи всех учитываемых процессов: A около 1.32 MiB/s, C около 2.52 MiB/s; это buffered/process counters, **не физическая скорость SSD**. PG connections 4–5; наблюдаемых Lock waits 0; остановок/автоматических перезапусков криптосервисов 0. Тестовые процессы остановлены штатной очисткой стенда по завершении.

**НЕ ПРОВЕРЕНО:** HTTP/auth/browser latency Spot/Futures под нагрузкой, реальный production профиль клиентов, конкурирующие реальные сделки, p95/p99 production за сутки, дисковые задержки Hetzner при новом модуле и tail latency длительного soak-теста. У API не найдены готовые агрегированные request-latency metrics; `/health` использован только для идентификации/доступности и не подменяет эти измерения. Краткие PG waits между снимками могли быть пропущены.

## Отказы и границы

**ИЗМЕРЕНО:** timeout, 429, 500, битый JSON, ответ >512 KiB, дубли, пропущенный интервал, убийство процесса внутри незавершённой SQLite-транзакции, временный write lock. На запрос максимум 3 попытки; нет неограниченной очереди, история стримится. Timeout завершился за 0.728 с после 3 попыток. При дублях после повторной записи 10 уникальных строк. После убийства посередине записи незавершённых строк 0; replay дал ровно 100 уникальных строк. Busy storage отказало за 0.225 с. Пропуск отмечен как gap, искусственная свеча не создавалась.

Logical-quota тест вернул `SQLITE_FULL` при ограничении файла 32 KiB. **Физическое заполнение отдельного тестового тома не проверено**: готового ограниченного тома нет. Системный диск и production не заполнялись. Глобальные настройки БД, расширения и логирование не менялись.

При отказе provider/collector крипто-сервисы не вызывают модуль акций и не зависят от него при запуске. D продолжает реальные fixture торговые операции без ошибок. Потеря доступности котировок должна приводить к stale/unavailable, а не к подставной цене. Процессная изоляция не устраняет конкуренцию за общий CPU/RAM/диск: это показал C.

Проверено 7 календарных fixture-границ: выходной, праздник, короткий день, DST, отдельная задержка данных, отсутствие нового интервала, азиатский перерыв. Это отдельные boundary-тесты, не интегрированный календарь нагрузочного сборщика и не подтверждение реальных биржевых календарей. Реальный планировщик должен учитывать каждый venue/timezone, обеденные перерывы, короткие дни и праздники; опрашивать только интервалы, закрывшиеся с учётом задержки публикации. Пересечение сессий определяет размер очереди, а 100 Asia пока остаётся модельным количеством. Вне сессии новые свечи не должны выдумываться. Retry-After и суточный credit budget будущего провайдера ещё должны быть реализованы; ускоренные 25/50 ms retries допустимы только в fixture-тесте.

## Что требуется до ограниченной интеграции

1. Сохранить отдельное хранилище и процесс; не давать сборщику доступ к финансовой PG. Crypto startup/health не должен зависеть от акций. Не переносить тестовый Python HTTP-сервер как готовую production службу.
2. Ограничить не только collector ≤0.2 vCPU/256 MiB, но и чтения/кеш, число параллельных ответов, очередь и общий бюджет модуля. Проверить суммарный пиковый RAM budget с резервом ОС: одновременные нынешние ceilings не дают гарантированного запаса. Не менять production limits без отдельного решения.
3. Первичный backfill делать вне торгового VPS либо с паузой при росте крипто-latency/CPU/I/O; не совмещать неограниченный backfill и массовые графики. Нужен реальный API latency baseline/monitoring и повтор проверки после выбора реализации чтения.
4. Предварительно: хранение 12 месяцев, hard budget history 256 MiB; остановка новых записей при свободном месте ниже **8 GiB** или нарушении лимита history/WAL. Ограничить WAL 16 MiB контролем записи и длительности read snapshots; один autocheckpoint не гарантирует лимита. Логи ограничить 16 MiB. Проверить восстановление stock snapshot, встроив его в существующий backup workflow, а не создавая второй бесконтрольный процесс.
5. Удалять только историю акций старше retention небольшими транзакциями. Удаление строк переиспользует страницы и не гарантирует уменьшения файла. Для освобождения места предпочтительны заранее спроектированные месячные stock partitions/файлы с безопасным закрытием читателей. Никакой очистки production в этой задаче не выполнялось.
6. До выбора поставщика проверить точные US/RU/Asia markets и MIC/symbol mapping, индексы отдельно от акций, interval=15m, закрытость свечи, delay, объём/volume для индексов, adjusted/unadjusted цены и splits, доступную глубину истории, лимиты и credits, caching/storage/export/redistribution rights. Ничего не приобреталось и пригодность поставщика не объявляется.

Текущий код подтверждает только существующий crypto gateway и ограниченный каталог CFD/FX/metals/energy; `StockMarketDataService` в архитектурном документе описан как **не реализованный**. Наличие 15m в CFD OHLC adapter не доказывает покрытие требуемых 250 акций/индексов или права их показа.

## Доказательства и воспроизведение

- `README.md` — точные локальные команды, параметры и ограничения.

Это не production incidents. Production SHA/start time сохранились; никаких миграций, перезапусков, финансовых записей, merge или deploy в этой задаче не было.
