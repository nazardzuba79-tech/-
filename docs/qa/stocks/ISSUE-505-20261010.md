# Issue #505: provider reuse and durable account contention

Review-only continuation of Draft PR #497. Baseline is `f81f404269bfe4b93c19443ce7fc8b881756a366`; fresh main is `a2290d4f26a1b2ddf71c045110a89f185fd968e6`. No deployment, production access, external orders, price/FX/P&L arithmetic change, or shared trading UI change.

## Changes and boundaries

Selected instrument/timeframe history requests may retrieve 600 native rows, retaining the public 300-row page. A second requested historical page is derived only when native order, cardinality and coverage prove the exact 300 rows before applying the existing strict `time < before` filter. Unproven ranges use the original provider path. Latest/history TTLs remain 10/300 seconds from source observation, with shared 128-entry/8 MiB accounting, bounded singleflight admission, and correction invalidation. No background catalogue history fetch or larger provider quota is introduced.

Trusted quote observations for accounts without an open order on that instrument now form a bounded volatile valuation projection. Read views use the unchanged engine calculations. Active-order observations still execute individual FULL/DELETE/BEGIN IMMEDIATE transactions, even when they do not fill. A new explicit order binds its trusted quote and consumed event capacity into its own durable financial transaction; no client-supplied quote enters that boundary. Canonical same-ID recovery precedes projection hydration. Cancellation, capital changes, fills, reserves and history remain durable.

The worker bounds projections by its existing 512 owner handles, the fixed catalogue, and a 4 MiB serialized quote-payload LRU. This payload limit is not a claim about total V8 memory. Eviction retains compact timestamp/event/capacity watermarks. Lost owner/worker authority imposes a conservative provider timestamp barrier at reload time plus the engine's existing 2-second future-skew allowance. Until then Market is rejected; a new Limit may reserve funds but cannot match an old fallback quote. Quiet sources can therefore take longer to recover. Durable financial state and histories survive; uncommitted display ticks need not survive. Ledger revisions and quote digests fence independent repository writes before admission.

Regression coverage includes correction/pagination/gaps/unknown intervals, latest-flight queue ordering, Alice/Bob, repeated event capacity, stale projections after another writer, owner eviction, failed commit, restart, explicit same-ID replay and cancellation/capital operations. Queue limits remain 128 commands/1 MiB/2.5 seconds; financial POSTs are never automatically retried.

## Measurement method

Both sides of the new realistic comparison use the same corrected synthetic native provider fixture: requested row limit is honored, Binance rows ascend, Bybit rows descend, and provider end is inclusive before the application's strict filter. The previous fixture always returned 300 and used an exclusive end. Workloads, users, cursors, duration, three repeats, thresholds and resources are unchanged, but these corrected-fixture comparisons must not be spliced into earlier absolute mock results. This verifies the fixture contract, not live provider inclusivity or data rights.

The deterministic provider replay reduces 156 transports to 100 and four RATE_LIMIT errors to zero. It increases response bytes 3,840,732 to 4,921,960 (+28.15%) and peak accounted cache to 7,968,960 bytes. Five local process microprofiles measured median CPU 31 to 62 ms; they exclude HTTP/SQL and are not a capacity result. These tradeoffs require the bounded CI measurements.

The original strict 50/100-reader and same-core crypto comparison remains intact against `3c5a6a73d014826c47a89541d4fe85b2fbc41761`. An additional identical comparison uses f81 as the immediate baseline. No read-service HTTP optimization was adopted: four rotated local Buffer/string/synchronous-handoff variants did not show a reproducible benefit. That code is byte-identical to f81; any new same-core variation cannot be attributed to a product HTTP change.

CI repeats 5/20/50 mixed/shared users, 20 instruments, 30 seconds, .05 vCPU/256 MiB and 3-second deadlines, with original 1 MiB/s read/128 KiB/s write caps and separately no artificial I/O cap. Raw metrics include all attempts/errors, success-only and all-attempt percentiles, CPU/RSS, SQL, aggregate fsync timings, queue occupancy, provider calls, and volatile versus durable observations. Green evidence collection is not a passed capacity gate.
